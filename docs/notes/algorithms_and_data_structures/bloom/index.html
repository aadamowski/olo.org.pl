Bloom filters: a probabilistic 'definitely not there'

Table of Contents

Probabilistic data structures — membership in a handful of bits

A Bloom filter answers one question — “have I seen this before?” — using a bit array far too small to store the items themselves. It never misses an item that was inserted, and it sometimes cries wolf: a false positive. That trade, a tiny memory footprint in exchange for a controllable error rate, makes it one of the most deployed ideas in systems software, from database engines to network routers.

The one-sentence idea. Hash each item with k different hash functions and set those k bits in an m-bit array. To query, check the same k bits: if any is 0 the item is definitely absent; if all are 1 it is probably present — the bits may have been set by other items. No false negatives, ever; false positives at a rate you choose when you size the filter.

1 — How it works: k hashes, m bits, nothing else stored

Burton Bloom described the structure in 1970. It has exactly two ingredients: a bit array of m bits, all initially 0, and k hash functions that each map an item to a position in the array. Nothing about the item itself is stored — no key, no pointer, no copy. The array is the whole data structure, which is why it is so small.

Insert xCompute the k positions and set each of those bits to 1. Setting an already-set bit changes nothing — inserts are idempotent, and bits are shared between items.
Query xCompute the same k positions. If any of them is 0, x was never inserted. If all of them are 1, report “probably present”.

How to read this

  • A 0 bit is proof. If a query finds any of its k bits at 0, the item cannot have been inserted — inserting it would have set that bit, and bits are never cleared.
  • All 1s is only a hint. The k bits may belong to k different other items. The filter cannot tell who set a bit.
  • Collisions are the mechanism, not a bug. With 5 items × 3 hashes in 32 bits, the five fruits set 15 distinct bits — nearly half the array — so collisions are already likely. Step 2 quantifies exactly how likely.

2 — False positives: the price, and how it grows

Why can there never be a false negative? A query for an inserted item checks bits that its own insertion set to 1, and in a standard Bloom filter bits never go back to 0. The answer for a true member is therefore always “present”. The error is one-sided by construction.

A false positive needs a conspiracy: every one of the query’s k bits was set by someone else. The more items inserted, the larger the fraction of bits set — the fill — and the easier that conspiracy becomes. After inserting n items, the probability that a given bit is still 0, and the resulting false-positive probability, are:

3 — Sizing math: pick p, get m and k

In practice you design backwards: you know roughly how many items n the filter must hold, and the false-positive rate p you can tolerate. Two formulas then fix the array size m and the hash count k. The derivation of the optimal k is short enough to do in full — and the key step is kept explicit, because the result (aim for a half-full array) is the most useful intuition in this whole page.

4 — Counting Bloom filter: buying deletion with counters

The standard filter cannot delete: a bit may be shared by several items, so clearing it on one item’s removal could evict others — creating false negatives, the one thing the structure promises never to do. The counting Bloom filter (Fan et al., 2000) replaces each bit with a small counter, typically 4 bits. Insert increments the k counters; delete decrements them; a query asks whether all k counters are above 0. An item can leave when its counters are no longer needed by anyone else.

Figure 4: Counting filter. m = 16 counters, k = 2, 0 items present

Figure 4. Insert cat and dog, then bird: notice any counter reaching 2: two items share it, so deleting one of them only drops it to 1 and the other stays findable. What the counters cost, and their limit

  • 4× the memory of a plain filter at the same m (4-bit counters instead of 1-bit flags) — or, at fixed memory, an m four times smaller and a higher p.
  • Counters can overflow. With 4-bit counters the ceiling is 15; Fan et al. showed that for typical sizing the chance any counter overflows is tiny, but implementations must still choose a policy (saturate, or size up) — a saturated counter can no longer be decremented safely.
  • Deletion must be truthful. Decrementing for an item that was never inserted — or was only a false positive — steals counts from real members and can manufacture false negatives.

5 — Variants: one idea, many shapes

Almost every limitation of the 1970 design has a named descendant. The table compares the main ones on the axes that actually decide deployments: whether items can leave, whether the set can grow, and what the structure pays for it.

Choosing, in one breath. Fixed known n and no deletion: classic (usually blocked) Bloom. Deletion needed: counting Bloom, or a cuckoo filter when p must be low. Unknown or growing n: scalable Bloom, or a quotient filter if you also need merges and resizes. The classic design remains the default because its query is a handful of bit tests with zero bookkeeping.

6 — Applications: a cheap “no” that saves expensive work

Every deployment has the same shape: an expensive operation — a disk read, a decompression, a network round trip — guarded by a filter whose “definitely not” lets the system skip the work entirely. A false positive merely wastes one expensive check; a false negative would lose data, so the one-sided error is exactly the right way round.

Caching

Cache digests & admission

  • Web cache digests: proxy caches such as Squid exchange Bloom-filter digests of what they hold, so a peer is only queried when the digest says “probably here” — turning an all-peers broadcast into a directed request.
  • CDN and browser caches: a compact summary of a remote cache’s contents avoids fetching objects the edge cache provably does not have.
  • Cache admission: “have we seen this key before?” filters keep one-hit wonders out of the cache — an item is admitted only on its second appearance, which the filter can attest cheaply.
Databases

Skipping disk reads in LSM stores

  • LSM-tree SSTables: LevelDB, RocksDB, Apache Cassandra and HBase keep a Bloom filter per data file. A point lookup checks the filter first; a “no” skips opening that file at all. With data spread over many files, this is the difference between one disk read and dozens.
  • Join and dedup guards: a filter over the keys already seen cheaply discards duplicates and non-matching rows before heavier join machinery runs.
  • Original motivation, still running: spell-checkers and hyphenation dictionaries were among the earliest uses — a huge word list compressed into RAM-sized bits, with rare false “correct” spellings as the accepted cost.
Networks

Forwarding & light clients

  • Packet forwarding: routers use Bloom filters to summarise which prefixes or subscribers sit behind an interface, compressing forwarding state that would not fit in fast memory as an exact table.
  • Bitcoin light clients (BIP 37): an SPV client sends its node a Bloom filter of the addresses it cares about; the node forwards only matching transactions. The known weakness is privacy — a loosely tuned filter matches too much and leaks interest — which is itself a lesson in what p means.
  • Ethereum block headers: each header carries a 2048-bit logs bloom aggregating the event-log addresses and topics in the block, so light clients can skip blocks that provably contain no log they follow.

The pattern generalises beyond these three: deduplication in backup systems, safe-browsing URL checks (shipped to browsers as compact prefix filters), and “seen this event ID?” guards in streaming pipelines all use the same move. Whenever a set is huge, the negative answer is the common case, and a rare wasted check is cheap — a Bloom filter is probably already there, quietly saying no.
